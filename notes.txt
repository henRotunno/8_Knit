1. The Size vs. Quality Trade-off:
    For our Knit project, we chose Qwen2.5-1.5B-Instruct, a language model developed by Alibaba's Qwen team and available through Hugging Face.
    The model has approximately 1.5 billion parameters, placing it in the small-model category (1B–3B parameters).
    We use a local AI feature that allows users to describe the type of activity they want to do over the weekend and receive an AI-generated recommendation.
    In our Django application, the local_llm_view function receives the user's prompt from a text box and passes it to the generate_local_response() function.
    The resulting text is then displayed on the page as an AI recommendation. For example, a user could enter, "I want something relaxing and indoors this weekend,"
    and the application would generate a suggestion based on that input. The best model size for our project should be determined by comparing the results of our 15-model tests.
    We would evaluate the models based on how relevant their recommendations are, how well they follow instructions, how consistently they generate useful responses, and how long they take to respond.

 2. Cost & Scaling:
    If Knit grew to 10,000 daily users, we would need to evaluate whether our existing local model could handle the increased number of AI requests. Our application currently has a local AI feature and a
    hybrid AI feature. The local feature sends user prompts to the Hugging Face model, while the hybrid feature uses a pipeline in which the local model acts as a pre-filter or guardrail and an external
    Groq API generates refined text. For Knit, I would consider keeping the local model for routine activity suggestions and using the Groq API for more complex requests. This would let us balance infrastructure costs, API spending, and response quality.
    Before making a final decision, we would need to measure our actual request volume, model latency, server utilization, and API usage.
    The hybrid pipeline has a different cost structure. DistilBERT performs the initial classification locally, but inputs that pass the filter are sent to Groq for text generation. Therefore, the hybrid pipeline still incurs API costs for requests that reach the external model.
    For example, if 10,000 users each made one AI request per day, with each request containing 500 input tokens and generating 200 output tokens, the application would process approximately 5 million input tokens and 2 million output tokens daily. If we used a hypothetical API rate
    of $0.50 per million input tokens and $2.00 per million output tokens, the cost would be approximately $195 per 30-day month.

  3. Hybrid Potential:
    Knit already includes a hybrid AI view that calls run_hybrid_pipeline() when a user submits text. According to our Django code, the pipeline uses two stages: the local Hugging Face model acts as a pre-filter or guardrail, and the external
    Groq API generates refined text. For example, a user might submit the following request: "I want something fun to do this weekend that is inexpensive and lets me meet new people."
    The local model could help process or screen the request before it reaches the external API. The Groq API could then generate a refined recommendation based on the user's interests. This could allow us to combine the efficiency of a smaller local model
    with the text-generation capabilities of an external service. The main advantage of a hybrid approach is flexibility. Knit could use a smaller local model for tasks it handles well and reserve the external API for requests that benefit from more advanced
    text generation. This could improve the user experience while helping us control costs as the application grows.

  4. Cost Comparison:
    For Knit, using a pre-trained model locally would be appropriate when the model can complete its task accurately and efficiently without requiring excessive computing resources. Our Qwen2.5-1.5B-Instruct model is intended for generating local activity suggestions,
